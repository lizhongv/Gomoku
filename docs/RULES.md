# 规则

> 适用版本：v2.0.0（开发中）
> 规则实现：`gomoku-core` 的 `RuleSet`、`WinDetector`、`GameState`

## 一、棋盘

- 默认 15×15，支持 19×19；坐标 `(row, col)` 从 0 开始，行列均自左上角计。
- 黑先白后，交替落子；已有棋子的点不能落子。
- 棋盘下满且无人五连为和棋。

## 二、无禁手（FREESTYLE）

- 任意一方形成五连及以上（横、竖、两条斜线）即获胜。
- 适合大众对局、人机练习与移动端。

## 三、连珠（RENJU）

- 黑方有禁手，白方不受限制。
- **黑方胜**：恰好五连。
- **长连**：六连及以上，黑方判负（禁手），白方仍算胜。
- **三三**：一手同时形成两个活三，黑方禁手。
- **四四**：一手同时形成两个四，黑方禁手。
- **五连优先**：一手若同时形成五连与其他禁手形态，判胜，不算禁手。

### 判定口径

禁手基于局部棋型计数：

1. 在目标点临时落黑子；
2. 若四方向最长连子恰好为 5，判胜（优先于禁手）；
3. 若最长连子 ≥ 6，判长连禁手；
4. 否则统计四个方向的棋型：四（活四或冲四）≥ 2 为四四禁手，活三 ≥ 2 为三三禁手。

**已知限制**：未实现连珠规则中的「假活三」递归排除（例如被堵死后并不真正成立的三），
因此个别边界局面可能与正式裁判不同。该限制在 `RuleSet` 的类注释中注明，正式比赛应使用专门裁判程序。

## 四、胜负与撤销

- `GameState.play(move)` 负责合法性、落子、胜负与和棋判定；不合法时棋盘不变。
- `GameState.undo()` 撤销最近一手并恢复行棋方；若上一手已分出胜负，撤销后由同一方继续。
- 界面、AI、服务端必须使用 `GameState`，不得自行维护另一套胜负逻辑。

## 五、AI 的规则约束

- `SearchLimits` 不包含规则；`GomokuEngine(size, ruleSet)` 在构造时绑定规则。
- 连珠模式下，黑方禁手点会被走法生成直接排除；VCF 同样只考虑合法着法。
- 白方在连珠模式下按无禁手处理。

## 六、阶段三的服务端裁决

服务端将持有唯一的 `GameState`：

- 客户端只发送「请求落子」，服务端校验轮次、坐标、占用、禁手与胜负；
- 客户端不得自行宣布胜利；
- 断线、超时与认输由服务端结算并写入棋谱。

这一条是商业化前提，v1 服务端信任客户端 `WIN` 的问题在 v2 中必须消除。
